# 方案 B：LLM 辅助 Diarization

## 核心思路

让 LLM 基于**台词内容**（剧情连贯性、口癖、第一人称、对话对象）来判断角色，**补充**或**修正**纯声学方案的输出。

```
传统:     声学 → SPK1/2/3/4 (声学相似就合并, 声线撞型就崩)
方案 B:   声学 → SPK1/2/3/4 → LLM 修正 → 修正后的标签
```

利用日语番剧的特点：角色台词常带强烈语言标识（口癖、第一人称、口吻），文本层面区分角色比声学层面更鲁棒。

## 三种子思路（按可行性排序）

### B1. 声学初分 + LLM 后处理（推荐）

```
1. pyannote/NeMo 跑出粗略的 SPK1/2/3/4 标签
2. Whisper 转写 (或直接用你的高质量字幕台词)
3. 把 "时间段 + 当前 SPK 标签 + 台词" 喂给 LLM
4. LLM 检测明显错误的归属并修正
5. 输出修正后的 SRT
```

LLM 干的事：
- 检测口癖一致性（"のじゃ" 这种角色口癖一定属于同一人）
- 检测对话连贯性（A 问的，回答应该是 B）
- 检测剧情语境（敬语对应长辈，亲昵对应朋友）

### B2. 参考字幕段 + LLM 推断

```
1. 你听一遍音频, 标几段已知是 X 角色说的
2. LLM 学这些 ground truth, 推断后续台词归属
3. 输出 SRT
```

不依赖声学，纯文本。

### B3. 纯文本无监督聚类（不推荐）

```
1. 把所有台词喂 LLM
2. 让 LLM 自行分组成 N 角色
```

没锚点容易乱分，短台词大量误判，**实测效果很可能不可用**。

## 适用场景

- 角色性格 / 语言特征明显（番剧/动画很常见）
- 你了解角色，能写出有效的 prompt
- 主要语种是 LLM 训练充分的语言（中文 / 日语 / 英文都行）
- 转写质量不能太差（LLM 是基于文本判断的）

## 不适用场景

- 大量短台词（"うん"、"そう"、"えっ"）—— LLM 也分不出来
- 角色语言特征极相似（双胞胎、同性别同年龄段闺蜜）
- 没有完整字幕且 Whisper 转写错误率高

## 完整流程（B1）

```
INPUT:
  - audio.wav
  - 高质量字幕 (替代 Whisper) 或 Whisper 转写结果
  - 角色介绍 (人工写, 包含名字/性格/口癖/第一人称)

STEP 1. 声学初分
  - 跑 pyannote, 得到 [(start, end, SPK1)...] 标签

STEP 2. 文本对齐
  - 把字幕台词和声学时间段对齐
  - 每条台词附带一个声学预测的 SPK 标签

STEP 3. 构造 LLM prompt
  - 角色介绍
  - 完整对话上下文 (序号 + 时间段 + SPK 标签 + 台词)
  - 任务说明: "请基于剧情连贯性和角色语言特征, 判断每条台词
              真正的说话人。如果声学标签正确就保留, 错误就修正。"
  - 输出格式: JSON [{idx, original_spk, corrected_spk, confidence, reason}]

STEP 4. LLM 调用
  - Gemini Flash / DeepSeek / Claude / GPT-4
  - 长上下文一次喂完整集 (Gemini 1M token 容易, 其他要分批)

STEP 5. 输出
  - 修正后的 SRT
  - confidence 低的标红, 供人工复核
  - 双向验证: pyannote 和 LLM 不一致的段落特别标记
```

## LLM 选择

| 选项 | 优点 | 缺点 | 月费估算（一部番剧 12 集） |
|---|---|---|---|
| Gemini 2.5 Flash | 1M 长上下文 + 免费额度大 | 需科学上网 | 几乎免费 |
| DeepSeek-V3 | 国内便宜，无审查 | 上下文 64K | ~5-15 元 |
| Kimi K2 | 国内长上下文 200K | 速度一般 | ~20-50 元 |
| Claude Sonnet | 推理强 | 贵 | ~200-500 元 |
| GPT-4o | 推理强 | 贵 + 内容审查 | ~300-800 元 |
| Qwen2.5-72B 本地 | 完全本地 | 需要 ≥40GB 显存 | 0 但买卡贵 |
| Qwen2.5-14B 4bit | 8-10GB 能跑 | 推理质量打折 | 0 |

**推荐顺序**：Gemini Flash > DeepSeek > Kimi > 本地

## Prompt 设计要点

### 1. 角色介绍要具体

❌ 模糊：
```
- Kaguya: 主角
- Iroha: 朋友
```

✅ 具体：
```
- Kaguya (かぐや): 22岁女性, 性格傲娇, 第一人称用 "わたくし",
  常用 "じゃ" 结尾, 对 Iroha 说话时会带 "あなた"
- Iroha (いろは): 18岁女性, 性格元气, 第一人称 "あたし",
  说话节奏快, 常用感叹词 "やった!" "うわー!"
```

### 2. 给 LLM 完整上下文

不要逐条问"这是谁说的"，要把整段对话都给它，让它看上下文：

```
[1] [00:01:23-00:01:25] SPK1: いろは, 本当に引っ越し?
[2] [00:01:25-00:01:28] SPK2: だって, かぐやどんどん物増やすでしょ?
[3] [00:01:28-00:01:30] SPK1: 失礼な!
```

LLM 看到 [2] 提到了 "かぐや"，那 [2] 就**不**是 Kaguya（不会自称名字），且 [1] 称呼 [2] 为 "いろは"，所以 [1] 说话对象是 Iroha，[2] 说话者就是 Iroha。

### 3. 要求结构化输出

```json
[
  {
    "idx": 1,
    "time": "00:01:23-00:01:25",
    "text": "いろは, 本当に引っ越し?",
    "original_spk": "SPK1",
    "corrected_spk": "Kaguya",
    "confidence": "high",
    "reason": "对 Iroha 说话, 推测为 Kaguya"
  },
  ...
]
```

### 4. 处理短台词

加一条规则：

> 对于无明显角色特征的短台词（"うん"、"そう"、"えっ"、"はい"），
> 保留原 SPK 标签，confidence 标 "low"，不强行修正。

## 工程实现要点

### 文件结构（如果实施）

```
diarize_llm.py              # 主脚本

  role_descriptions.json    # 各角色的介绍 (你来写)

  llm_corrected.srt         # 修正后
  llm_audit.json            # LLM 详细输出 + reason
  conflicts.txt             # 双向不一致清单
```

### 配置（diar_config.json 新增）

```json
"llm": {
    "provider": "gemini",        // gemini / deepseek / kimi / openai / local
    "model": "gemini-2.5-flash",
    "api_key_env": "GEMINI_API_KEY",
    "batch_size": 50,            // 每批喂多少条字幕给 LLM
    "context_window": 10,        // 前后多少条作上下文
    "low_confidence_threshold": 0.6
}
```

## 优点

- **不需要训练模型**——LLM 现成可用
- **不需要参考音频**——比方案 A 门槛低
- **能处理声线撞型**——文本特征不依赖声线
- **顺便做转写校对**——LLM 还能修正 Whisper 的明显错误

## 缺点

- **短台词无解**（占比常 30-50%，是硬上限）
- **需要懂角色**——你要能写出有效的角色介绍
- **token 消耗**——长番剧一集几千条字幕，token 成本 0.1-2 元
- **网络依赖**（除非用本地小模型，但效果差）
- **隐私问题**——台词上传到 LLM 服务商
- **一致性风险**——LLM 偶尔会幻觉，需要后处理验证

## 双向验证机制（必加）

LLM 不可全信，最稳的做法：

```
对每条台词, 比较 pyannote 和 LLM 的判断:

case 1: 一致 → 高信心, 直接采用
case 2: 不一致 + LLM 给出强 reason → 用 LLM, 标 "声学修正"
case 3: 不一致 + LLM 给出弱 reason → 标 "高风险", 进人工审听
case 4: LLM 自己说 "low confidence" → 用 pyannote, 标 "声学优先"
```

输出三级目录：
- `confirmed/` — 两边一致或单方高信心
- `corrected/` — LLM 修正了 pyannote
- `manual_review/` — 高风险，需人工

## 进阶：多模态 LLM

有些 LLM 已经支持音频输入（Gemini, GPT-4o-audio）。理论上能直接给一段音频 + 上下文台词，让它判断角色。但：

- API 价格更贵
- 当前模型对说话人分离能力未必比专门模型好
- **不推荐作为首选**，除非纯文本方案完全失败

## 现有商业 / 开源参考

- **AssemblyAI LeMUR**: 转写后用 LLM 后处理（不专门做 diarization 修正，但思路相似）
- **WhisperX + GPT 后处理**: 社区有人做，主要修转写错误
- **NExT-GPT / SALMONN**: 多模态大模型，研究阶段
- **学术界**: 搜 "LLM-assisted speaker diarization" / "text-aware diarization"，2024 起渐多

## 何时选 B 而不是 C

- 你没有带说话人标注的字幕
- 但你有完整台词 + 了解角色

## 何时选 B 而不是 A

- 你找不到每个角色的干净参考音频
- 角色语言特征非常明显
- 你愿意接受 LLM 的不确定性

## 推荐使用场景

**作为方案 C 的补充**：
- 主流程用方案 C（字幕驱动切片）
- 字幕里没标注的角色或不确定的部分，用方案 B 兜底

**作为方案 A 的补充**：
- 主流程用方案 A（enrollment）
- LLM 检查 enrollment 输出的 "_uncertain/" 目录，做二次判断

## 实施前需要准备

1. **角色介绍文档**（最关键）
   - 每个主要角色 100-200 字
   - 包含：名字、性别、年龄、第一人称、口癖、典型台词
   - 越详细 LLM 越准

2. **LLM API key**
   - 推荐 Gemini Flash（免费额度足够测试一部番剧）

3. **完整台词**
   - 字幕文件（最佳）
   - 或 Whisper large-v3 转写

## 风险提示

不要指望 LLM 给你 100% 准确率。即使在最好的情况下：
- 有口癖的角色：90%+
- 普通对话：70-85%
- 短叹词：50%（接近随机）
- 总体：75-85%

**这个准确率对 TTS 训练数据准备来说已经够用**——剩下的人工抽听筛掉错误片段即可。
